## 2. Что изменилось по задачам

### TASK 1 — Морфологическая фильтрация (morphology.py, geo_matcher.py)
- `Lemma` получил `pos` и `is_prep`; `Morphology.lemmatize_tokens` возвращает POS-теги.
- Новый статический `Morphology.is_geo_candidate()` + `is_preposition()`.
- **Эмпирическое отклонение от буквы ТЗ в пользу его цели:** наивное исключение `VERB/INFN/ADVB/INTJ/PRCL/CONJ/PRED/COMP/GRND` ломает recall — pymorphy3 уверенно ошибается на OOV-проперах (`Гаванная`→GRND, `героив`→GRND) и даже на предлогах (`на`→INTJ, `в`/`с`→NOUN-abbrev). Это прямо запрещено R-PR29. Поэтому:
  - токен исключается только если **все** его альтернативные разборы — не-топонимные POS (без Geox/Name/Surn/UNKN);
  - **stem-rescue:** окно не выбрасывается, если хоть один его стем присутствует в гео-индексе (OOV-пропера спасены);
  - `PREP` (уверенность ~100%, одиночный разбор) → не участвует в матчинге, служит **границей скользящего окна** (окна не склеиваются через предлог). Проверено: ни один алиас гео-объекта не содержит отдельного предлога → сегментация безопасна.
- Фильтр включён по умолчанию: `enable_pos_filter: true` (+ env `GEO_ENABLE_POS_FILTER`).

### TASK 2 — GeoMatcher: полнота и longest-match-first (geo_matcher.py)
- Скользящее окно собирает **всех** валидных кандидатов по всем сегментам (без остановки на первом матче); продолжен учёт чисел в длине окна.
- **Longest Match First** через двухступенчатый finalize: (1) спан-вложенность — суб-спаны внутри большего спана того же сегмента отбрасываются; (2) floor-скор `1 − 0.02·(max_w − size)` компенсирует fuzz-штраф inflection-форм — верные длинные матчи больше не проваливаются под `candidate_min_score`.
- Падежные формы: стем-матч (Snowball) уже нормализует падеж; «французского» поднято с 0.783 → **0.960** (было отброшено SQL-порогом 0.80).

### TASK 3 — Стратегия и резолвер (settings.py, 16-process-candidates-v2.sql)
- Семантического резолвера в проекте нет по дизайну (R-PR9/R-PR27 — geometry-first, стратегию выбирает PostGIS). Задача ТЗ отображена на `process_candidates_v2` + Python-пороги:
  - `weighted_centroid_max_scatter_m`: **1000 → 500** (env `GEO_WEIGHTED_CENTROID_MAX_SCATTER_M`);
  - SQL default scatter 1000 → **500**;
  - `best_single` переупорядочен: **score DESC** первым, затем line-type/длина — соответствует «максимальный скор побеждает»;
  - `random` невозможен при кандидате ≥ порога: порог применяется ДО арбитража (constraint 4).

### Сопутствующие исправления
- `Morphology.shrink_cache()` реализован (в R-PR4 memory-fallback вызывался несуществующий метод — латентная ошибка).
- `tests/test_geo_matcher_tier2.py`: стаб-лоадер перезаписывал реальный `processor.morphology.Lemma` на `object` при уже импортированном модуле → перекрёстное загрязнение тестов (воспроизводилось и на немодифицированном дереве). Исправлено: сначала попытка реального импорта.
- Ограничение импорта `_NON_GEO_POS` сделано совместимым со стаб-лоадером тестов.

## 5. Замечание о производительности (важно для прода)

Профилирование оффлайн-прогона (без executor) показало **~7 с/сообщение**, ~95% времени — Tier-2 `rapidfuzz.process.extractOne(fuzz.WRatio)` по полному списку алиасов (~4k) для каждого «мусорного» окна: `Слободская` на «Аккордная — Мельницкая блокпост в обе стороны…» порождает окна-мусор (после/за/между…), каждое сканирует весь словарь.

В проде `ProcessPoolExecutor(max_workers=4)` маскирует проблему, но: (а) CPU-бюджет растёт линейно с потоком сообщений; (б) fallback на синхронный путь при таймауте executor деградирует до секунд на сообщение.

**Рекомендация (вне рамок этого рефакторинга):** `process.cdist` batch-скоринг (тот же WRatio в C-цикле, ~50–100× на batch) или bm25/трикрограммный префильтр кандидатов перед WRatio. Для batch-оценки использован параллельный харнесс `scripts/eval_live_parallel.py` с точным (parity-checked) cdist-ускорителем.
